# 06. 정리와 운영 전환

> 실험 결과를 회고하고, 이번 실행의 역할과 유료 자원을 정리한 뒤 부재까지 확인합니다.

이전: [05. 로그 검증](05-rbac-event-validation.md) · [홈](../README.md)

## 목표

- preview의 모든 대상과 정확한 확인 문구를 읽고 승인합니다.
- 임시 역할과 전용 RG의 삭제 요청뿐 아니라 실제 부재를 확인합니다.
- 부분 실패·미기록 외부 역할을 구분하고 운영 전환에 남은 과제를 정리합니다.

## 예상 소요 시간

15분. Azure 삭제 대기가 길어져도 완료 확인을 생략하지 않습니다.

## 시작 전 상태

- 성공·실패 여부와 관계없이 이번 실습의 `STATE_FILE`과 증거를 보존했습니다.
- Module 01의 공통 함수를 복구하고, 삭제할 대상이 이번 실행 소유인지 확인할 수 있습니다.
- 이전 장이 실패했다면 이 장으로 바로 이동합니다. 로그 검증 성공은 정리의 전제조건이 아닙니다.

## 회고

👁️ **설명**

정리 전에 다음 세 문장을 자기 증거로 설명해 봅니다.

1. 이번 Reader의 대상·역할·scope는 무엇이며, 어떤 Activity Log에서 확인했나요?
2. 같은 할당의 수신·실행 성공을 무엇으로 연결했고, 수신 지연과 수집 지연은 각각 무엇인가요?
3. 토픽 지표만으로 특정 이벤트의 전달이나 감사 로그의 무손실을 단정할 수 없는 이유는 무엇인가요?

증거가 불완전하면 성공이라고 기록하지 않습니다. 회고나 로그 수집을 마치지 못해도 비용 자원의 정리는 진행합니다.

## 1. 삭제 preview

[선택 실습 05A](05a-companyname-validation.md)를 수행했다면 먼저 해당 장의 `scripts.companyname cleanup`이 완료되어야 합니다. 이 장의 기본 정리는 신규 Entra 사용자나 Graph 권한을 추측해 삭제하지 않습니다. 05A에서는 구독 Reader가 `disabled`가 아니라 `recorded`인 것이 정상이며, 이 장에서 정확한 해당 역할까지 제거합니다.

👁️ **설명**

01의 `STATE_FILE`·공통 함수를 복구합니다. 같은 계정·테넌트·사용자와 전용 RG 소유 태그를 확인한 뒤, **모든 삭제 대상**의 사용자·역할·scope를 먼저 검증합니다. 확인되지 않은 대상이 하나라도 있으면 삭제를 시작하지 않습니다.

🟢 **실행**

```bash
preview_cleanup() {
  restore_workshop || return
  python3 scripts/workshop.py cleanup "$STATE_FILE" --dry-run
}
preview_cleanup
```

📋 **확인**

`resourceGroupId`, `testAssignmentId`, `subscriptionReader`, `confirmation`을 직접 읽습니다. 이번 RG와 자기 테스트 ID만 나와야 합니다. 정상 워크숍의 구독 Reader는 `disabled`입니다.

확인 문구 형식은 **`DELETE <이번 runId> FROM <이번 subscriptionId>`**입니다. 이 예시 자리 표시자가 아니라 **실제 preview의 문자열 전체**를 입력해야 합니다.

⚠️ **주의**

미리 보기는 Azure를 변경하지 않습니다. 단순히 이름 접두사가 비슷하다고 소유권으로 인정하지 않습니다. 403은 부재가 아니며, 태그 불일치 때 태그를 억지로 맞추어 삭제하지 않습니다.

## 2. 정확한 대상 삭제와 완료 확인

🟢 **실행**

```bash
delete_workshop_run() {
  restore_workshop || return
  local confirmation
  read -r -p "preview의 confirmation 전체를 입력하세요: " confirmation || return
  python3 scripts/workshop.py cleanup "$STATE_FILE" --confirmation "$confirmation"
}
delete_workshop_run
```

📋 **확인**

도구는 **기록한 테스트 역할 → 기록·검증된 구독 Reader가 있으면 그 역할 → 전용 RG** 순서로 삭제하고 부재를 기다립니다. RG 삭제만 요청하고 완료라고 표시하지 않습니다. `resourceGroupRemoved=true`, 구독 Reader가 기록되었다면 `subscriptionReader=removed`를 확인합니다.

`.workshop-state/<실행ID>/cleanup.json`에 결과가 남습니다. Portal → **리소스 그룹**에서 이번 RG가 없어졌는지, **구독 → IAM**에서 기록된 외부 역할이 남지 않았는지 교차 확인합니다. 삭제 전용 증거를 확인한 뒤에도 비용 집계에는 지연이 있을 수 있습니다.

⚠️ **주의**

코드·상태·증거는 Cloud Shell의 로컬 파일로 남습니다. 여기에는 사용자 Object ID 등 환경 정보가 있으므로 비공개 보관 정책을 적용합니다. 보관 기간이 끝나면 파일 탐색기에서 **정확한 이번 상태 파일과 이번 실행 디렉터리만** 삭제합니다. 홈·저장소 전체나 다른 실행 디렉터리를 재귀 삭제하지 않습니다.

## 트러블슈팅

👁️ **설명**

배포·게시·시험 역할 생성이 실패해도 같은 상태 파일로 preview를 다시 수행합니다.

| 상황 | 동작과 다음 확인 |
|---|---|
| 출력 capture 전 배포 실패 | 소유 태그가 검증된 RG만 정리 가능. `subscriptionReader=not-recorded`이면 구독 역할이 없다고 증명한 것은 아님 |
| Reader 생성 응답 유실 | 예약 GUID로 실제 사용자·역할·scope를 확인한 뒤 그 ID만 정리 |
| 다른 대상·역할·scope 발견 | 아무 삭제도 하지 않고 중단. 관리자에게 비공개로 원본 상태·해당 ID 전달 |
| 조회 403 | 권한 오류 해결 전 중단. “이미 없음”으로 간주하지 않음 |
| RG가 먼저 사라짐 | 기록된 구독 Reader가 있으면 역할과 남아 있는 구독 배포 출력으로 소유권 증명 후 정리 |
| 삭제 3분 대기 초과 | 완료라고 표시하지 않음. 같은 상태로 Portal 삭제 진행 상태 확인 후 preview·cleanup 재시도 |

🟢 **실행**

```bash
python3 scripts/workshop.py cleanup "$STATE_FILE" --dry-run
```

📋 **확인**

이미 RG와 기록된 역할이 없어도 재실행할 수 있습니다. 출력 없는 부분 실패에서는 `not-recorded`를 주의해서 읽고 Portal → **구독 → 배포 → 이번 infra/events 배포 → 작업 세부 정보**를 검토합니다. 워크숍 명령은 구독 Reader를 만들지 않지만, 옵션을 누락한 수동 배포는 별도 감사해야 합니다. 도구는 **기록되지 않은 구독 역할을 추정해 삭제하지 않습니다.**

⚠️ **주의**

전체 구독에서 Reader 역할을 모두 지우거나 기존 시스템 토픽을 삭제하여 “정리”하지 않습니다. 잔존 역할의 소유권을 증명할 수 없으면 관리자 확인 전 그대로 보존하고 정리 미완료로 기록합니다.

## 운영 전환 전에

👁️ **설명**

이 실습은 실시간 수신 가능성을 확인하는 출발점이지 감사·컴플라이언스 완성품이 아닙니다.

| 운영 과제 | 추가 설계 |
|---|---|
| 중복·역순·일시 실패 | 멱등성, 재처리 큐·dead-letter, 재조정 작업과 중복 식별 |
| 실제 사용자·역할명 보강 | ARM 일관성·삭제 경합, Graph 최소 권한·동의·개인정보 처리 |
| 로그 누락·수집 지연 | 로그 제한·보존·수집 상태 경보, Activity Log 장기 보관·독립 감사 경로 |
| 모니터링 | 전달 실패·함수 실패·관측 공백 경보와 운영자 대응 |
| 네트워크 | Event Grid 수신·모니터링까지 포함한 요구사항별 사설화 검토 |
| 접근·비용 | 로그 읽기 RBAC, 보존·삭제 정책, 예산·서비스 한도 |

📋 **확인**

전달 성공은 비동기 Function 실행 성공과 다를 수 있습니다. 기본 샘플링을 꺼도 로그가 절대 누락되지 않는 것은 아닙니다. `companyName`은 이 저장소의 현재 출력이 아니며, 자동 보강을 운영에 넣을 때는 별도 구현·권한 승인이 필요합니다.
