# 구독 RBAC 이벤트 수신 워크숍 설계

작성일: 2026-11-15

상태: 사용자 검토 대기. 수신 중심 접근은 선택되었으며, 아래 상세 설계는 아직 승인되지 않았다.

## 1. 목적과 선택한 접근

참가자가 자기 실습용 Azure 구독에서 RBAC 할당 이벤트의 생성, 필터링, 함수 실행, 로그 수집을 직접 확인하고 안전하게 정리할 수 있는 한국어 핸즈온을 만든다.

참고 저장소는 `https://github.com/freeman9844/ms-landing-zone-02`이며 게시 대상은 `https://github.com/freeman9844/event-rbac-test-01`이다.
학습 순서와 문서 표현 방식을 참고하되 원문, 코드, 화면 이미지를 복사하지 않는다.

검토한 접근은 다음과 같다.

| 접근 | 장점 | 제약 | 결정 |
|---|---|---|---|
| 검증된 수신기 중심 워크숍 | 실제 동작을 확인한 이벤트 경로를 참가자가 재현하며 Graph 관리자 동의가 불필요하다. | 수신 함수가 사용자 이름, 역할 이름, 회사 정보를 자동 보강하지 않는다. | 사용자가 선택했다. |
| ARM·Graph 보강을 먼저 완성한 워크숍 | 최초 구상의 사용자·역할·회사 정보를 최종 로그에서 확인할 수 있다. | 추가 앱 구현과 검증, Entra 관리자 동의 단계가 필요하다. | 이번 범위에서 제외한다. |

기존 `subscription-rbac-companyname` 설계의 후속 ARM·Graph 작업을 완료한 것으로 표시하지 않는다.

## 2. 학습 목표와 제외 범위

참가자는 다음을 완료한다.

- 작업 수행자와 역할을 부여받는 대상을 구분하고 Event Grid claims만으로 대상을 추론하지 않는다.
- 전용 RG에 Python 3.11 Flex Consumption Function, 사설 Storage, 모니터링과 네트워크를 배포한다.
- 수신 코드를 게시한 다음 Event Grid를 연결하는 순서를 이해한다.
- 자기 사용자에게 전용 RG Reader를 잠시 부여하고 정확한 할당 ID를 보관한다.
- Activity Log, Event Grid 지표, 함수 실행 로그와 Application Insights 수신 로그를 대조한다.
- 자기 실행의 임시 역할과 유료 리소스를 정리하고 부재까지 확인한다.

사용자·역할명·`companyName` 자동 조회, Graph 권한 부여, 그룹 구성원 확장, 삭제 이벤트 감시, PIM 전체 수명주기, 무손실 감사 원장과 운영 가용성 보장은 제외한다.
대상 사용자와 Reader 역할은 실습 수행자가 Activity Log 요청 본문 및 역할 정의를 별도로 대조한다.

## 3. 참가 환경과 제약

다음은 참고 형식과 기존 구현을 바탕으로 정한 설계 제안이다.

- 참가자 명령은 저장소 루트의 Cloud Shell Bash를 기준으로 작성한다. Azure CLI, Bicep, Python 3와 필요한 기본 도구를 사전 확인한다.
- 기존 Windows 개발 안내는 별도 개발자 안내로 남긴다. Bash 실습과 PowerShell 명령을 같은 실행 블록에서 혼합하지 않는다.
- 사전 준비에서 테넌트, 구독, 로그인 사용자, 공급자 및 Flex 지원 지역을 확인한다. 기본 구독을 몰래 전환하지 않고 명령마다 구독을 명시한다.
- 배포와 테스트에 필요한 구독 리소스 생성, Event Grid 관리, 역할 할당 권한을 명시한다. Contributor만으로 역할 부여까지 가능하다고 안내하지 않는다.
- 소스인 구독마다 시스템 토픽은 하나만 허용된다. 참가자별 독립 실습 구독을 전제로 하며, 동일 구독의 동시 실행은 지원하지 않는다.
- 기존 구독 소스 시스템 토픽을 발견하면 새 생성 전에 중단한다. 기존 토픽의 재사용, 수정, 삭제는 하지 않는다.
- VNet은 다른 네트워크와 연결하지 않는 전용 실습망이다. 기존 네트워크, DNS와 운영 리소스는 변경하지 않는다.
- Storage는 공개 네트워크·익명 Blob·공유 키 접근을 비활성화한다. Function 수신 HTTPS와 모니터링 엔드포인트까지 완전 사설화한 것으로 설명하지 않는다.
- Graph 동의나 기존 Azure 리소스의 변경은 이번 교재 제작·GitHub 게시 과정에서 수행하지 않는다.

시스템 토픽 제약의 근거: <https://learn.microsoft.com/azure/event-grid/system-topics#system-topics-as-azure-resources>

## 4. 교재 구조

README는 학습 목표, 구성·이벤트 흐름 Mermaid 그림, 요구 권한, 비용, 번호형 목차, 중단·복구 및 정리 안내를 제공하는 시작 페이지로 바꾼다.

| 모듈 | 주제 | 확인할 결과 | 목표 시간 |
|---|---|---|---:|
| 00 | Azure·RBAC·Event Grid 첫걸음 | 구독·RG·역할·이벤트·로그의 관계 | 10분 |
| 01 | 실습 준비 | 권한, 충돌 점검, 고유 실행 ID와 상태 파일 | 15분 |
| 02 | 인프라와 사설 Storage | 관리 ID, VNet, PE, DNS, Function, 모니터링 | 25분 |
| 03 | 수신 코드 게시 | 소스 전용 ZIP 원격 빌드와 함수 등록 | 15분 |
| 04 | Event Grid 연결 | 정확한 이벤트 유형·작업명·함수 대상 | 10분 |
| 05 | 실제 RBAC 이벤트와 로그 | 새 Reader 할당, 시각·할당 ID·실행 ID 대조 | 20분 |
| 06 | 정리와 운영 차이 | 정확한 역할·전용 RG 삭제와 부재 확인 | 15분 |
| 합계 | | | 110분 |

배포와 로그 수집 지연에 따라 실제 시간은 늘어날 수 있다고 명시한다.
각 장은 목표, 공통 준비, 설명·실행·확인 블록, Portal 확인, 문제 해결, 완료 체크 및 이전·다음 링크를 제공한다.
설명·실행·확인·주의 표시는 참고 교재처럼 분리된 줄로 표현한다.
핵심 Azure 명령과 필터·로그 필드는 교재에 드러내며 전체 과정을 불투명한 원클릭 명령으로 숨기지 않는다.
실제 측정 예시와 참가자가 자신의 환경에서 확보해야 하는 증거를 구분한다.
새 화면 이미지를 꾸며 넣지 않고, Mermaid와 Portal 확인 경로를 사용한다.

## 5. 보조 코드와 상태

기존 Python 수신기와 Event Grid 필터 의미는 유지한다.
보조 도구는 기존 Python 표준 라이브러리와 Azure CLI를 재사용하며, 상태·포장·안전 검증·정리에 필요한 최소 기능으로 제한한다.
새 앱 런타임 의존성이나 일반 목적의 배포 프레임워크를 추가하지 않는다.

`.workshop-state/<실행 ID>.json`에 상태 버전, 테넌트·구독, 실행 ID, 전용 RG, 지역, 접두사, 고유 배포 이름, 배포 출력과 이번 임시 역할 ID를 기록한다.
상태와 실행 증거, ZIP, 환경 파일 및 `.superpowers` 실행 자료는 Git에서 제외한다.
토큰, 공유 키, Function 키와 전체 claims는 상태나 로그 증거에 기록하지 않는다.
새 실행과 기존 실행 복구를 구분하고 원래 상태를 덮어쓰거나 추정하여 복구하지 않는다.

필요한 Bicep 보조 변경은 전용 RG 소유 태그, 정리에 필요한 정확한 출력 및 수신 전용 과정에 불필요한 Function 구독 Reader를 선택적으로 생략하는 옵션으로 제한한다.
기존 PoC 호출의 기본 동작은 유지하되 워크숍 명령에서는 해당 Reader 옵션을 명시적으로 끈다.
증분 배포에서 옵션을 끄는 것만으로 기존 역할이나 이벤트 구독이 삭제되지는 않는다는 점을 안내한다.
구독 범위 배포 이름은 실행별로 구분하여 다른 실행의 배포 출력과 섞이지 않게 한다.

## 6. 검증과 안전한 정리

실제 RBAC 테스트는 승인된 현재 사용자와 이번 전용 RG의 Reader로 제한한다.
기존 동일 할당이 있으면 삭제·교체하지 않고 중단한다.
생성 전 GUID와 정리 대상을 저장하고, 생성 응답의 대상·역할·범위를 확인한다.
검증 실패나 중간 종료 뒤에도 정확한 ID로 자기 임시 역할을 찾을 수 있어야 한다.

로그 검증은 새 할당 ID로 Activity Log와 수신 로그를 연결하고, 동일 InvocationId 또는 OperationId로 함수 성공을 대조한다.
Event Grid 지표는 명시적 UTC 시간 범위를 검증한 토픽 집계로 취급하며 개별 이벤트 로그로 가장하지 않는다.
표본 없음과 측정값 0, 이벤트 처리 시각과 로그 수집 시각, 앱 역할 범위와 Workspace 범위를 구분한다.
이번 관측에서 eventId와 Activity correlationId가 같았더라도 일반 계약으로 만들지 않는다.

정리는 먼저 전체 삭제 대상과 소유 정보를 읽기 전용으로 확인하고 정확한 확인 문구를 요구한다.
이번 테스트 역할, 이번 실행이 선택적으로 만든 구독 Reader, 전용 RG 순으로 정리하고 부재를 확인한다.
RG 바깥의 구독 역할은 RG 삭제만으로 정리되지 않는다는 점을 명시한다.
조회 오류를 리소스 부재로 취급하지 않으며, 소유권 불일치 때는 삭제를 진행하지 않는다.
기존 PoC, 다른 참가자, Cloud Shell 저장소, 구독 자체와 운영 리소스는 삭제 대상이 아니다.

## 7. 완료 기준과 게시

- 기존 수신기 테스트와 새 상태·포장·검증·정리 안전성 테스트가 통과한다.
- Bicep 컴파일, 관련 정적 검사와 문서 링크·명령·파일 구성 검사가 통과한다.
- 파괴적 정리 동작은 모의 Azure CLI로 실패·권한 오류·소유권 불일치·부분 실행을 검증한다.
- 새 워크숍 전체를 실제 Azure에 재배포했다고 주장하지 않는다. 별도 승인 없는 추가 배포는 하지 않는다.
- 기존 실제 측정 결과는 환경 식별자를 제거한 참고 예시로만 사용한다.
- 게시할 파일과 Git 이력을 확인해 환경 ID, 비밀과 비공개 실행 자료를 제외한다.
- 대상의 기존 내용을 강제 덮어쓰지 않고 `main`에 일반 push한 뒤 원격 HEAD와 실제 README·모듈을 확인한다.

현재 대상은 공개 빈 저장소이며 기본 브랜치는 `main`이다.
현재 확인한 인증은 API에서 push 권한이 false이고 Git dry-run도 403으로 거절됐다.
실제 동기화 완료에는 대상 저장소의 쓰기 권한 또는 사용자가 직접 준비한 적법한 Git 인증이 필요하다.
공유 개발 환경의 GitHub 계정을 임의로 전환하거나 토큰을 문서·명령·대화에 기록하지 않는다.

## 8. 검토

기존 README, 세 Bicep 템플릿, 수신 함수와 실측 로그 구조, 참고 교재의 README·준비·실습·정리 장 및 공식 시스템 토픽 제약을 대조했다.
자체 설계 점검에서 기존 토픽 충돌, Contributor만으로 부족한 역할 부여 권한, RG 외부 Reader 잔존, 로그 시각·지표 해석 및 게시 권한을 주요 확인 항목으로 반영했다.
